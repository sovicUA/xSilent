# План: 3 типи сповіщень + вибір голосу

Робочий документ. Призначення — дати будь-якій сесії Claude Code (або людині)
повний контекст для реалізації, не переказуючи обговорення. Доповнює
[DECISIONS.md](DECISIONS.md).

**Статус:** узгоджено напрям, не почато. Дата: 2026-09-09.
**Область:** лише Android. iOS — окремо й пізніше (вибір голосу переноситься
легко; будильник на iOS кастомно неможливий).

---

## 1. Мотивація

Після внутрішнього тесту 1.1.0 від користувачів надійшло:

1. **Вибір голосу** для озвучення сповіщень.
2. **Тип «Будильник»** — сповіщення з поведінкою будильника: дзвінок по колу
   протягом заданого часу (напр. 1 хв) → авто-відкладання на N хв → «Вимкнути»
   або «Відкласти», як у звичайних будильниках.

Підсумок: застосунок отримує **3 типи сповіщень**:

| Тип | Опис | Кількість |
|---|---|---|
| `builtin` | Хвилина мовчання (вбудоване) | рівно 1, сідиться `reconcile()` |
| `reminder` | Нагадування користувача (поточна поведінка) | 0..N |
| `alarm` | Будильник користувача | 0..N |

## 2. Модель даних (schema v6 → v7)

### Заміна `isBuiltIn` на `type`

```dart
enum ReminderType { builtin, reminder, alarm }   // зберігати як int: 0/1/2
```

- Нова колонка `type` (int, default 1 = `reminder`).
- Міграція `from < 7`:
  `UPDATE reminders SET type = 0 WHERE is_built_in = 1;`
  (решта лишається `type = 1`).
- `isBuiltIn` лишити як **computed getter** `type == builtin` на першому етапі,
  щоб не переписувати всі місця виклику одразу; згодом прибрати колонку.

### Нові колонки (значущі лише для `type = alarm`)

| Колонка | Тип | Default | Призначення |
|---|---|---|---|
| `alarmRingSeconds` | int | 60 | скільки триває один дзвінок |
| `alarmSnoozeMinutes` | int | 5 | інтервал авто-відкладання |
| `alarmMaxCycles` | int | 3 | скільки авто-відкладань, поки не здатися |

### Голос (глобально, не per-reminder)

- `ttsVoiceName` — `String?` у `shared_preferences` (ключ `tts_voice`),
  `null` = голос рушія за замовчуванням.
- **Не** колонка в `reminders`: користувачі очікують «голос застосунку», а не
  окремий на кожне нагадування. Менше UI-шуму.

### Що вже є і працює для всіх типів

`hour`, `minute`, `weekdayMask`, `enabled`, `title`, `body`, `speakAloud`,
`announcementVolume`, `preNotify` / `preLeadSeconds`. `tickDuringSilence` —
лишається лише для `builtin`.

## 3. Вибір голосу

### Дизайн

- `flutter_tts.getVoices` → `List<{name, locale}>`; `setVoice({name, locale})`
  перед `synthesizeToFile`.
- **Головний ризик — мережеві голоси.** Google TTS для `uk-UA` має локальні
  (`...-local`, `...-embedded`) і мережеві (`...-network`). Мережевий у
  `synthesizeToFile` **offline не працює** (тиша / помилка). Застосунок
  офлайн-first, тож:
  - фільтрувати список за підрядком `network` у `name` (крихко, але дешево), **або**
  - лишити всі, але після синтезу перевіряти розмір/тривалість файлу й при
    провалі падати на дефолтний голос + показувати підказку.
  - Рекомендація: фільтр за `name` + перевірка результату як запобіжник.
- Набір голосів дуже різний по рушіях (Google / Samsung / Huawei) і пристроях.
  На частині — 1 укр. голос або жодного. UI має коректно показувати «Голосів не
  знайдено — використовується стандартний».
- Якщо збережений `ttsVoiceName` зник на новому пристрої / після оновлення
  рушія — тихо відкотитися на дефолт і пере-синхронізувати.

### Точки інтеграції

| Файл | Зміна |
|---|---|
| `lib/services/tts_service.dart` | `configureTts`: після `setLanguage`, якщо голос обрано й доступний — `setVoice`. Приймати ім'я голосу параметром. |
| `lib/services/announcement_service.dart` | `_hash` включає ім'я голосу → зміна голосу перегенеровує всі канали/файли озвучення. `build`/`preview` приймають `voice`. |
| `lib/services/notification_service.dart` | `sync`/`reconcile` протягують `voice` у `AnnouncementService` (як зараз `volume`). |
| `lib/screens/settings_screen.dart` | новий розділ «Голос озвучення»: список доступних укр. голосів + «Стандартний», кнопка прослухати зразок. |
| `lib/screens/edit_reminder_screen.dart` | прев'ю використовує обраний голос. |
| провайдер | `ttsVoiceProvider` (як `localeControllerProvider`), зміна → `reconcile()`. |

### Оцінка: ~1 день

- 0.5 дн — енумерація + фільтр голосів + UI в налаштуваннях.
- 0.25 дн — проброс голосу у хеш + build + preview.
- 0.25 дн — тест на пристрої (імена голосів, мережеві голоси — ризикова частина).

## 4. Тип «Будильник»

### Архітектурна напруга

Уся філософія застосунку ([DECISIONS.md](DECISIONS.md), «Option A»): **жодного
фонового виконання; усе — заплановане `zonedSchedule` сповіщення із запеченим
звуком каналу.** Рішення вистраждане після того, як `android_alarm_manager_plus`
виявився ненадійним на Motorola (Android глушив фонове аудіо застосунку вдень).
«Справжній» будильник (миттєва зупинка звуку, справжній цикл, повноекранний UI)
цьому суперечить.

### Стратегія A — ланцюг сповіщень (у межах поточної архітектури)

Будильник = заздалегідь заплановані ітерації `zonedSchedule`:

- `T` — дзвінок. Звук каналу = WAV, зациклений до `alarmRingSeconds` (гонг+голос
  повторюється, як зараз метроном заповнює 60 с). `fullScreenIntent: true` —
  поверх локскріна. Кнопки: **Вимкнути**, **Відкласти**.
- `T + ring + snooze`, `T + 2·(ring+snooze)`, … — планувати `alarmMaxCycles`
  ітерацій наперед. Кожна = авто-відкладання.
- **Вимкнути** → фоновий ізолят (`notificationActionCallback`) скасовує всі
  майбутні ітерації цього будильника.
- **Відкласти** (натиснуто раніше) → скасувати поточну + переставити ланцюг від
  «зараз».
- Нічого не робити → наступна ітерація спрацьовує сама (це і є авто-snooze).

**Плюси:** перевірений механізм; працює коли застосунок вбито; мінімум
нативного коду; узгоджено з метрономом/передсигналом.

**Мінуси / чого бракує справжньому будильнику:**

1. **Звук не зупиняється миттєво.** `_plugin.cancel(id)` ховає банер, але на
   багатьох пристроях канал **дограє WAV до кінця** (до `alarmRingSeconds`).
   Це головний UX-розрив. **Треба перевірити спайком** (див. §6).
2. Немає живого UI (відлік, велика кнопка) — лише банер + повноекранний intent,
   що відкриває окремий екран застосунку.
3. `alarmRingSeconds` запечений у WAV → 5 хв ≈ 14 МБ на будильник. Прийнятно для
   1–2 хв.
4. Вібрація каналу — фіксований короткий патерн, не циклиться на всю тривалість.
5. Точність ланцюга залежить від точних будильників (дозвіл є).

### Стратегія B — нативний сервіс (справжній будильник)

`AlarmManager.setAlarmClock()` (найпріоритетніший API, іконка будильника в
статус-барі, Doze-exempt) → `BroadcastReceiver` → **foreground-сервіс**:

- wake lock;
- `MediaPlayer`/`ExoPlayer` `setLooping(true)`, `USAGE_ALARM` — справжній цикл;
- повноекранне сповіщення → Flutter-екран «дзвінок» (або нативна активність);
- після `alarmRingSeconds` без реакції → стоп аудіо, `setAlarmClock` на
  +`alarmSnoozeMinutes`, сповіщення «відкладено»;
- **Вимкнути** → стоп сервіс, скасувати наступний;
- **Відкласти** → стоп аудіо зараз, `setAlarmClock` на +snooze.
- Місток Flutter ↔ сервіс через MethodChannel.

**Плюси:** реальна поведінка — миттєва зупинка, справжній цикл, іконка
будильника, Doze-exempt. Так працюють усі будильники.

**Мінуси:** значний обсяг Kotlin (сервіс, ресивер, MediaPlayer, wake locks,
екран дзвінка); нові дозволи + декларації в Play (`USE_FULL_SCREEN_INTENT` —
з Android 14 лише для alarm/calendar-застосунків; тип foreground-сервісу);
OEM (Xiaomi/Huawei) все одно можуть вбити сервіс — потрібен UX «вимкнути
оптимізацію батареї».

### Рекомендація

**Спочатку Стратегія A**, після спайка §6. Якщо `cancel()` зупиняє звук чисто —
A цілком достатньо для будильника. Якщо ні — оцінити, наскільки розрив
критичний за фідбеком внутрішнього тесту, і лише тоді вкладатися в B (можна
частково: нативний сервіс тільки для відтворення дзвінка, а тригер і snooze
лишити на `zonedSchedule` / `setAlarmClock`).

## 5. UI (обидві стратегії)

- **Головний екран:** 3 секції — «Хвилина мовчання» (вбудоване, закріплене) /
  «Нагадування» / «Будильники». FAB → меню «+ Нагадування» / «+ Будильник».
  Порожні секції ховати.
- **Редактор:** спільна база (час, назва, дні, звук, гучність, передсигнал) +
  секції за типом. `_isBuiltIn` → `_type`. Будильник показує `ringSeconds` /
  `snoozeMinutes` / `maxCycles`; ховає «метроном хвилини мовчання».
- **Новий екран «дзвінок будильника»:** великий час, «Вимкнути» /
  «Відкласти (+N хв)». Ціль повноекранного intent (A) або керований сервісом (B).

## 6. Спайк (перед етапом 3) — 0.5 дн

На пристрої (Motorola Edge 50 + Lenovo TB305XU) перевірити 2 питання, що
вирішують життєздатність Стратегії A:

1. **Чи зупиняє `flutter_local_notifications` `cancel(id)` звук каналу, що вже
   грає?** Запланувати сповіщення з довгим (30–60 с) WAV, за 5 с після
   спрацювання викликати `cancel(id)` (і/або натиснути кнопку дії з
   `cancelNotification: true`), у `dumpsys`/логах подивитися, коли реально
   зупиняється `AudioTrack`.
2. **Чи показується `fullScreenIntent: true` поверх заблокованого екрана** на
   обох пристроях (Android 15/16), і чи потрібен рантайм-дозвіл
   `USE_FULL_SCREEN_INTENT`.

Результат спайка → запис сюди й у DECISIONS.md.

## 8. Відкриті питання (вирішити до етапу 3)

- [ ] Ланцюг snooze: `alarmMaxCycles` ітерацій наперед — скільки саме за
  замовчуванням? (3? 5?) Що після останньої — тиша чи фінальне тихе сповіщення?
- [ ] `alarmRingSeconds` — діапазон у UI (напр. 15–120 с, крок 15)?
- [ ] Звук будильника: той самий `main_gong`/`additional_gong` + голос, чи
  окремий гучніший тон? Чи давати вибір?
- [ ] Повноекранний екран дзвінка — окремий маршрут у застосунку; що показувати,
  якщо будильників кілька спрацювало поспіль (черга)?
- [ ] Чи має будильник передсигнал (`preNotify`) — імовірно ні, ховати для
  `alarm`.
- [ ] Міграція `isBuiltIn` → коли прибирати колонку (окремий etap чи одразу в v7).
